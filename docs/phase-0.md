# RimLazy：全殖民地工作分配设计

目标是让玩家设定殖民地战略，由 MOD 管理执行。首版负责整张工作表：玩家调整战略、招募新人或有人受伤后，点击一次「重新计算并应用」。殖民者之后按游戏规则挑选实际任务。本阶段定义算法和验证方法，游戏接口以本机目标版本的代码与实测为准。

## 一次计算需要的数据

游戏适配层在按钮触发时导出快照；优化核心只读可序列化的数据。建议按以下契约构建第一组离线样例。时间统一为同一规划期内的游戏工作小时。

| 记录 | 关键字段及含义 |
| --- | --- |
| 快照 | `schemaVersion, gameBuild, activeModIdsAndVersions, mapId, horizonHours`。保存原表、战略、算法版本与参数，允许重放。 |
| 殖民者 | 稳定 ID、预计可劳动小时、有效工作属性、技能、激情、能力和角色限制。即时速度与培养收益分开记录。 |
| 工作表 | 游戏实际提供的工作列 ID、提供任务的 WorkGiver ID、允许的优先级及其执行顺序、当前单元格值和玩家锁定。稳定 ID 与显示语言分开。 |
| 任务与需求 | 任务或一批同类任务的 ID、所属工作列、订单剩余工作量、允许工人、技能门槛、可用材料、工位或其他共享资源 ID 与同时可用数量。需求区分已知、估计、未知；零代表确实无任务。 |
| 战略与偏好 | 各方向最低工时份额、剩余权重、工作到方向的贡献比例、即时产能/品质/培养/改表成本的权重、无权重余量的处理方式。 |
| 输出 | 建议优先级及改动清单、各方向目标和预计工时、未分配小时、缺口及原因、使用了哪些估计。应用前保留旧表供撤销。 |

## 从战略到工作表

1. **先把意图换成工时预算。** 设共有 `B` 小时可劳动，方向 `s` 的最低份额为 `m[s]`，剩余权重为 `w[s]`。当最低份额合计低于 100% 且权重和大于零时，该方向的目标小时为 `B × (m[s] + (1 − Σm) × w[s] / Σw)`。从 0.3.1 起，最低份额合计超过 100% 时，目标小时改为 `B × m[s] / Σm`。最低份额合计达到或超过 100% 时余量为零。所有权重均为零且还有余量时，按玩家选择保留原设置或留作未分配。任何方向的最低份额和权重都可设为零。
2. **分配到有实际需求的任务。** 以「某人给某项任务多少工时」为变量。排除游戏禁止、订单指定人不符及未达门槛的组合。每人分配的工时受其预算限制；任务剩余量按对应工人的预计速度折算；共用同一设备的不同订单合计占用该设备的时间。工作跨多个战略时拆分贡献，一小时最多记一小时。未知需求保留来源与估计，不能直接当成无限订单。
3. **在可行空间中取舍。** 先尽量降低各方向最低目标的工时缺口，再降低实际分配与战略目标的偏差；在相近方案中，用可调的即时效率、品质、培养和改表成本挑选。禁做的任务和玩家锁定是硬约束。锁定「禁用」意味着该人不能通过这列接任务；锁定「优先级 1」只固定优先级，不能据此预支工时。在连续规划阶段记录这类排序约束，到生成工作表时按真实档位评估。并列时按稳定 ID 择解。
4. **把计划变成玩家能用的表。** 以连续计划生成初始排序，按当前适配层报告的档位填表。用已核实的同档顺序、任务门槛和设备占用来估算这张表的效果，然后小范围升降或交换未锁定格子，按同一目标比较。搜索预算固定，返回遇到的最好结果与残余偏差。新增工作列出现在未映射清单中，供玩家指定战略归属；未验证的写入接口保持原值并标明原因。

举例：三名殖民者在同一八小时班次内各可工作八小时，且研究必须占用唯一一张研究台。即使战略要求 100% 科研，研究台最多支撑 8 个科研工时，约占 24 个可劳动工时的三分之一。方案应同时显示目标 24 小时、工位上限 8 小时，以及余下时间的处理方式；不能把预计科研占比写成产出保证。

## 1.7 需要实证的部分

| 待核实 | 在目标版本的验证方法 |
| --- | --- |
| 真实工作列、任务来源与顺序 | 对照本机 1.7 游戏程序集及 Def，核对 `WorkTypeDef`、`WorkGiverDef` 和实际任务选择逻辑，记录构建号、类型与成员。导出一个测试殖民地，与工作表逐列对照。 |
| 能否执行、先做哪项 | 用一位有工作禁令的殖民者、一个技能受限或指定工人的订单、两个同优先级且均可执行的工作，分别对照实际资格和选择顺序。区分被某个订单排除和整列工作都不能做。 |
| 优先级读写、保存及回滚 | 查证设置接口、手动优先级模式的行为和可用档位，在隔离存档中改一格，核对界面、保存重载和撤销结果。整表应用前复查快照所依据的列和格值；写入失败时恢复已改格并报告结果。 |
| DLC、工作表扩展与代理模型误差 | 先跑目标版本原版基线，再测试玩家实际使用且影响工作的扩展。以工位冲突及订单耗尽场景比较游戏记录和离线预计工时，说明偏差来自何处。 |

## 分阶段验收

- **离线核心**：合成快照覆盖全科研/零生存、全部权重为零、最低份额超限、不可工作、训练权重为零、锁格、新工作及不同优先级档位。同一快照重复求解产生相同结果。
- **有限任务及共享工位**：订单完成、材料用尽和工位释放时才推进模拟；验证不超出人员预算、不重复计算设备容量、缺口可追溯。设事件数上限；库存循环时报告循环。
- **1.7 实机闭环**：导出快照，在离线核心重现方案，点击一次写回，对照实际工作选择，再验证存档、重载和撤销。编译成功或离线断言通过均不能代替此项。

后续可沿用相同快照接入库存、生产订单和种植规划。库存模块可先把缺口转换成需求，生产模块再估算所需工时、设备与原料，由工作分配统一比较。新增模块若要自动创建订单或调整种植区，应另行定义触发条件、玩家锁定、写回与撤销的范围，避免不同模块同时改动同一决定。
