# 1.7 工作表兼容范围

RimLazy 读取当前地图可见的 `WorkTypeDef`、各列加载完全部补丁后的 `workGiversByPriority`，以及在场殖民者已初始化的工作设置。工作列和锁定分别用 `defName` 和「殖民者存档 ID + 工作 defName」保存。安装或移除增加工作列的模组后，重新预览即可。

## Complex Jobs 与自定义列

分类优先采用玩家的设置。其他列按工作标签匹配，例如 `Caring` 对应生存，`Constructing` 对应建设，`Crafting` 对应工业。本机 [FSF] Complex Jobs 1.7 的 `FSFNurse` 和 `FSFSurgeon` 都可以按 Caring 识别，并分别对每个殖民者判断工作禁令、任务所需能力与适任度。带固定工作台的标准配方列还会检查当前可用的订单、指定工人和配方技能要求。无法归类的列会列入映射页并保留原设置，玩家可以指定其战略。默认同时保留灭火、就医、卧床和基础事务列，玩家可逐列调整。

## 四档、六档与其他数量

本机 RimWorld **1.7.5005 rev1082** 的 `Pawn_WorkSettings.LowestPriority` 常量是 4。工作表的 0 代表停用，1 最优先。反查该构建的 `Pawn_WorkSettings.CacheWorkGiversInOrder` 后可见，普通工作优先比较玩家档位，档位相同时优先选择较大 `WorkTypeDef.naturalPriority` 的列；列内另有 `WorkGiverDef.priorityInType` 顺序。任务是否存在、距离、预留、紧急任务逻辑仍影响实际选择。

| 加载的工作表 | RimLazy 取得档位的方式 |
| --- | --- |
| 原版 | 读取当前游戏程序集的原版上限。原版 `SetPriority` 收到大于 4 的值会记录日志但仍存储它，因此不会用试写 5 或 6 探测支持情况。 |
| 有对应接口的 PriorityMaster | 仅在 `lauriichan.prioritymaster` 已启用时，读取已加载程序内的 `PriorityMod.Core.PriorityMaster.settings.GetMaxPriority()`。这套签名在本机旧版 PriorityMaster 中核对过，其原作者包只声明至 1.6。 |
| 其他使用标准工作列、0 停用、1 最优先的扩展 | 如果扩展没有报告上限，先在游戏自身的「工作」页为一个在场殖民者设置实际最高档位（例如 6）。RimLazy 会从当前已保存的格值识别 1–6。手动上限可以限制范围，也必须有当前提供者或实际格值支持。 |
| 外部模组接入 | 活动模组可调用 `StrategicWork.RimWorld.PriorityCompatibility.RegisterRange("作者.packageId", () => 当前上限)`。回调必须返回该模组的实际设置；RimLazy 在预览、应用及撤销时重新读取。若有多个提供者，以共同支持的范围为准。 |
| Fluffy Work Tab 的逐小时或逐任务优先级 | 可预览。该模组的聚合写入会修改整天或整列子任务，RimLazy 会保留这些细节并阻止写入、撤销。[作者的兼容说明](https://github.com/fluffy-mods/WorkTab) |

预览后若人员、档位、工位、订单资格、锁定或原表值改变，应用会停止并提示重新预览。开启游戏的手动优先级后才可写入。撤销只认上次应用后仍保持原样的目标格，同时复查当前档位；若旧值超出当前范围，整个批次都不会写入。遇到其他扩展拒绝改值时，会尝试还原本次已写入的格子并提示结果。

## 工时估计的口径

- 每个可工作的在场殖民者默认提供一个同班劳动力单位；倒地者保留原表且提供零工时。游戏的时间表、走路和休息时间会影响实际劳动。
- 纯标准配方列按有活跃订单的可用工作台数估计同时作业人数。订单原料、路线以及剩余产品数量造成的工时差异需在游戏中体现。
- 研究列识别当前研究项目可用的研究台，也计入同一工作列管理的扫描仪、研究对象或可骇入目标。这些是潜在工位。其他模组给这列附加新类型的任务时，容量显示为未知。
- 开放工作（如搬运、清洁、种植）的持续需求未知，离线估计可能高于实际投入。任务耗尽时殖民者按工作表继续寻找其他已启用的工作。
