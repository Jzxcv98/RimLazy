# RimLazy 0.3.2 实玩日志回归

2026-11-13，Windows，RimWorld 1.7.5005 rev1082。检查了上一轮对局的六份控制台日志、事件记录和出错前后的两个隔离存档。事件记录包含 41 次应用（含读档后的重试）。三次测试驱动中断分别发生在写进度文件、记录商队货物、应用 RimLazy 分工。

## 一张做到一半的短弓订单

出错前的检查点记录了制作点 `CraftingSpot93549`，弓胚 `UnfinishedWeapon95693` 已绑定到短弓订单。制作者 Peterson 随后倒地，制作优先级仍为 2。异常发生后第 1,764,144 tick 保存的文件里，工单的绑定已清空，弓胚仍在，剩余工量为 1357.769。

直接读取故障后的文件时，旧版已看不到原触发条件。用隔离副本和游戏的工单 API 恢复前一个检查点证实的关联，再调用实际分工窗口，0.3.1 的预览清除了绑定。两次采集间没有推进模拟，制作列的预计工作量仍从 0.090518 变成 0.112，应用因此拒绝写入。原版 `Bill_ProductionWithUft.BoundWorker` 在制作者倒地等情况下会清理绑定。

0.3.2 先按原版条件只读判断能否续作，给每次预览保留一致的工单快照。能继续的半成品只抵扣本件的工时。例如订单还需四把弓时，第一把取剩余工量，其余三把取完整工量。预览后暂停订单或手工改格，仍会阻止旧方案写回，并提示变化的岗位或格子。

## 两类搬运工作

在本轮真实工作表里，设施勤务和普通物资入库属于不同列。旧版会给两列套用相同的入库路线。新版从加载后的工作提供者识别物资入库、尸体入库、蓝图和框架送材；设施勤务继续用自己的工况估计，互不重复计入。

## 验证方法

- 纯核心使用 `scripts/test.ps1 --no-restore`。
- 事故回放使用 `scripts/smoke-game.py --campaign-save <隔离事故存档> --player-package <解压后的发行目录>`。运行器保留原存档，只在副本中移除自动玩家的测试计数组件，加载地图、人员、工单和原有工作表。旧版与新版比较的是相同的弓胚、制作者和工单。
- 默认实机场景在新地图上建立独立的真实短弓多件工单，验证半成品抵扣、材料和人员资格。另用真实储区和建筑蓝图区分入库、送材和设施勤务。这些用例可在没有历史测试存档的机器上重建。

## 发行包结果

36 项离线测试全部通过。事故回放（5 人、41 列）通过 10 项检查，常态与赶工可在同一个暂停 tick 内预览、应用和逐格撤销。真正改变工单或手工修改工作格后，原预览仍被拒绝。简中默认配置通过 96 项检查，156 个任务归属与对照目录一致；导入原有设置的 47 列配置通过 60 项。三次运行均无游戏错误，两个中文场景均无翻译警告。

三次实测使用的产品 DLL 与发行 ZIP 中的 SHA-256 一致。已逐一核对本机 Steam 安装目录中的 22 个文件。发行 ZIP 的 SHA-256 为 `8b0bc58704c335f64d1d6660c818de2201265277eae4e6e88f65585f7974f267`。
